## 一、 背景与业务目标

### 1.1 历史痛点
以往当用户完成一次跑步、徒步或骑行并从 iPhone 导出数据后，从压缩包到前端网页展示存在多道割裂的人工步骤：
1. **手工解压与环境切换**：需手动将 `导出.zip` 复制到 `apple_health_export` 目录执行合并；
2. **缺乏增量感知**：无法自动提取“本次到底新增了哪几条运动”，需要肉眼比对日期；
3. **命名规范脱节**：Apple 导出的文件名为 `route_2026-09-04_7.12pm.gpx`，需手动编写脚本或人工重命名为中文语义格式（如 `running-中国-广东-傍晚跑步-20260904.gpx`）；
4. **手工分步触发**：重命名后需手动拷入 `~/.config/gpx`，再切换到博客仓库手动执行 `update-tracks`。

### 1.2 核心目标
建立一条**高内聚、全链路复用、零人工干预**的一键式增量闭环：
- **用户操作仅需一步**：把 iPhone 导出的 zip 包下载到 Mac，运行 `./run.sh synct`；
- **系统全自动执行**：智能锁定 zip $\rightarrow$ 复用上游流式心率对齐 $\rightarrow$ 离线逆地理语义重命名 $\rightarrow$ 安全归档 $\rightarrow$ 驱动山河足迹 Go 流水线 $\rightarrow$ 前端即时热更新。

## 二、 架构设计与职责边界

系统严格遵循【单一职责、高内聚抽象、全链路复用】原则，划分为两大引擎各司其职：

```
                    ┌──────────────────────────────────────────────┐
                    │ 用户从 iPhone 导出【导出.zip】(或自动感知 Downloads) │
                    └──────────────────────┬───────────────────────┘
                                           │
                                    终端一条命令：
                                    ./run.sh synct
                                           │
                                           ▼
┌──────────────────────────────────────────────────────────────────────────────────────┐

│  1. 增量状态机：CacheManager (.processed_cache.json) 毫秒级差集比对                      │
│  2. 内存流式扫描：HealthMerger 单遍高效扫描 导出.xml 中的 HKQuantitySample                │
│  3. 双层对齐引擎：GpxProcessor.align_heart_rate                                        │
│     - 10 分钟聚合均值：endDate 区间无缝填补覆盖（彻底根除断崖式大空白）                     │
│     - 瞬时高频采样点：<=30秒平滑线性插值（还原生理连续起伏）                             │
│     - 生理极限清洗：30 <= hr <= 240 bpm                                                │
│  4. 产出物：高保真带心率 GPX 增量集合 (workout-routes-with-hr/*.gpx)                   │
└──────────────────────────────────────────┬───────────────────────────────────────────┘
                                           │ (产出带 99%+ 真实心率的高精 GPX)
                                           ▼
┌──────────────────────────────────────────────────────────────────────────────────────┐
│ 【调度中枢：shell/script/sync_tracks_pipeline.py 桥梁编排】(轻量极速驱动)              │
│  1. 智能数据包感知：自动探测 ~/Downloads 等路径中的【导出.zip】                         │
│  2. 触发增量心率对齐：调用 apple_health_export 导出高精带心率 GPX                       │
│  3. 一键交棒：调用 go run cmd/update-tracks/main.go --import-dir <temp_routes_dir>   │
└──────────────────────────────────────────┬───────────────────────────────────────────┘

                                           ▼
┌──────────────────────────────────────────────────────────────────────────────────────┐
│ 【下游：山河足迹 Go 生产流水线】(cmd/update-tracks 增量归档与生产一体化中枢)             │

│     - 全球 300+ 万地名精准识别，中国 34 个省级行政区规范简称，自动剥离冗余后缀            │
│     - 结合 FeatureClass (居民点/山地/林区) 与坡度高程智能推断运动类型 (徒步/越野跑等)      │
│  2. 语义规范命名与幂等安全归档：                                                      │
│     - 格式化为 {type}-{国家}-{省份}-{时段运动}-{YYYYMMDD}.gpx                          │
│     - 依据 StartTime 唯一性进行幂等去重检测，同日同类型运动自增防覆盖 (_1, _2)          │
```

## 三、 六阶段数据流转模型

### 阶段 1：智能数据包探测 (Auto-Ingestion)
调度器按照以下优先级策略自动查找可用的数据包：
1. 命令行显式传入的绝对/相对路径：`./run.sh synct /path/to/my_export.zip`
2. 用户最常接收隔空投送的默认目录：`~/Downloads/导出.zip` 或 `~/Downloads/export.zip`
3. 桌面备选：`~/Desktop/导出.zip` 或 `~/Desktop/export.zip`
4. 历史目录：`~/Developer/code/python_code/apple_health_export/导出.zip`
5. `~/Downloads/` 下最新修改的 `*导出*.zip` 或 `*export*.zip` 模式匹配。

### 阶段 2：增量感知与流式对齐 (100% 复用核心库)
- 在调用 `HealthMerger` 前，读取 `.processed_cache.json` 获得集合 `before_keys`；
- 执行 `merger.run(force=False, custom_src=zip_path)`，流式完成心率注入；
- 重新加载缓存获得 `after_keys`，两者差集 `new_fnames = after_keys - before_keys`；
- **若差集为空**：提示“所有轨迹此前已处理完成”，耗时仅 0.02 秒，安全退出；
- **若有增量**：提取仅属于本次新增的 GPX 文件，送入阶段 3。

### 阶段 3：全内存 3D KD-Tree 离线逆地理与规范命名 (100% 统一复用 internal/track)
增量 GPX 由 Go 核心流水线接管，调用 `internal/track/geo.go` 中成熟的 `photools/pkg/geocoding` KD-Tree 引擎：
- **纯内存极速查询**：单次反查仅需 200ns，零外部网络依赖与磁盘 IO 阻塞；
- **标准化行政区划**：自动规范省份（如剔除“壮族自治区”、“维吾尔自治区”等后缀，统一为“广东”、“新疆”、“西藏”等）；
- **地貌特征判定**：依据 FeatureClass（居民点、山地、风景区）与坡度海拔，智能区分城市散步、城市路跑、山地越野跑与高山徒步；
- **时段推断（东八区 CST）**：智能推导凌晨、早晨、上午、中午、下午、傍晚、晚上；
- **规范命名模式**：`{type}-{国家}-{省份}-{时段运动}-{YYYYMMDD}.gpx`  
  *示例：`route_2026-09-04_7.12pm.gpx` $\rightarrow$ `running-中国-广东-傍晚跑步-20260904.gpx`*

### 阶段 4：幂等去重与安全归档 (Safe Archiving)
- 目标路径：`~/.config/gpx/`
- **幂等性保障**：比较起始时间 `StartTime` 与运动类型，若目标库已存在完全相同运动，自动跳过，绝不产生重复垃圾文件；
- **冲突防覆写**：若发现同日同类型但起跑时间不同的多次运动，自动递增添加后缀 `_1`, `_2`，安全保护历史文件。

### 阶段 5：山河足迹 Go 生产流水线 (cmd/update-tracks)
自动通过 asdf 环境调用 `go run cmd/update-tracks/main.go --import-dir <temp_routes_dir>`：
1. **时空单调性保障**：使用 `slices.SortStableFunc` 稳定保序，杜绝点位逆序与时间倒流；
2. **高程峰谷滤波**：Peak-Valley 动态滤波剔除数千米虚假爬升，保留 0m 海平面与新疆负海拔；
3. **分片生成与抽稀**：输出 `web/tracks/data/overview.geojson` 与 `web/tracks/data/tracks/*.json`；
4. **摄影时空对齐**：统一 CST 时区，严格在 1km 范围内关联单反摄影作品；
5. **孤儿分片垃圾回收**：安全清理历史无用分片，输出体积减少 40% 的紧凑 `manifest.json`。

### 阶段 6：终端报告与热更新
终端输出本次新增入库的每一条轨迹卡片，本地预览服务器（`:3000`）热更新生效。

## 四、 日常使用指南与操作 SOP

日常从 iPhone 记录运动后，只需 **3 步**：

```
Step 1: 手机导出
在 iPhone 打开「健康」App ➡️ 点击右上角头像 ➡️ 滑动到底部点击「导出所有健康数据」
通过 AirDrop（隔空投送）或网盘发送给 Mac，默认保存在「下载」目录（~/Downloads/导出.zip）
       │
       ▼
Step 2: 终端一键闭环
打开终端，进入本博客项目目录，敲入命令：
./run.sh synct
       │
       ▼
Step 3: 浏览器点亮足迹
打开 http://localhost:3000/tracks/（或直接刷新页面），最新轨迹与心率 HUD 曲线已点亮！
```

### 常用命令变体
| 使用场景 | 命令格式 | 说明 |
| :--- | :--- | :--- |
| **标准日常同步** | `./run.sh synct` | 自动从 `~/Downloads/` 锁定最新的 `导出.zip` 并增量运行 |
| **指定特定文件** | `./run.sh synct ~/Desktop/export_0904.zip` | 显式指定任意位置的数据包 |

| **强制全量重对齐** | `python3 shell/script/sync_tracks_pipeline.py --force` | 忽略 `.processed_cache.json` 缓存，全量重跑 |

## 五、 容灾降级与防御性设计

1. **增量幂等性**：
   若用户不小心多次运行 `./run.sh synct`，`apple_health_export` 的缓存机制会在 0.02 秒内识别并提示“无新增量”，不会造成任何重复归档或数据破坏。
2. **多设备轨迹隔离**：
   非 Apple Watch 轨迹（如悦跑圈 `joyrun_*`、两步路下载的五台山 GPX、车载自驾记录）不会被该增量脚本触碰，保持纯净隔离。
3. **零外部 Python 库依赖**：
   逆地理引擎直接基于项目内的 `web/tracks/data/provinces.geojson` 使用纯标准库射线算法，不需要 `pip install` 任何第三方包，保证在任何机器环境上即开即用。
4. **孤儿分片防误删保护**：
   Go 流水线内建了安全比例校验，若扫描轨迹数量出现非预期断崖缩减，会自动拒绝执行清理，防止线上分片被破坏。
